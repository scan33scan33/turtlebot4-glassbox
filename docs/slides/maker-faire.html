Technology · architecturewhy “glassbox”?

The generated program is inspectable.

Before a wheel turns, we can read the script. During a run, we can see the map, path, detections, push line, and active skill.

Opaque robot policy

  • Motor behavior is buried in learned weights
  • A bad run is hard to explain
  • Fixing it means more data or training

This robot

  • Claude proposes readable code
  • A* + geometry decide motion
  • A failed test becomes a specific script change
At runtime, the only neural net labels objects. It does not steer.

Technology · behavior codea tiny action language

Claude writes readable .toy scripts.

Claude combines bounded robot skills instead of inventing wheel commands.

# push_ball_to_wall.toy (simplified)
SET ball = SCAN_FOR("ball", 360)
IF ball != NONE THEN
    SET r = PUSH_AWAY(ball.x, ball.y, 0.40)
    IF r == "stalled" THEN
        PRINT "pinned — done"
    END
END
0.40 = push one 40 cm segment, then stop and look for the ball again.

Action vocabulary

SCAN_FOR FIND PUSH_AWAY PUSH_TO_GOAL PUSH_THROUGH FOLLOW EXPLORE

Why this boundary?

  • Read the plan before a test
  • Unit-test it with MockRobot
  • Failures have names: stalled · lost · blocked
Technology · selectioncommand → installed script

A tiny matcher chooses what runs.

1 Exact trigger first

Each script lists phrases. The longest matching phrase wins with score 1.0.

"push the ball" → push_ball_to_wall

2 Otherwise, word overlap

Compare command words Q with the script’s description + triggers W.

score = |Q ∩ W| / √(|Q| + 1)
“follow the dog” → match_program() → follow_dog.toy → FOLLOW("dog")
The matcher only selects a script. It does not steer, plan, or invent a new behavior at showtime.

Deep dive · visionthe only neural net in the runtime

Vision in one sentence.

A neural net learns a pixels-to-label function from examples: here it returns “sports ball, 93% sure, right here.”

? What YOLO returns

  • An object label from 80 COCO classes
  • A bounding box in the image
  • A confidence score; we keep ≥ 0.3

! Where it runs

  • On the OAK-D camera’s VPU
  • About 6 detections per second
  • Offline, leaving the Pi free to plan
YOLO says what and where. It never says which way the wheels should turn.
Deep dive · sensor fusionsimple and fast

Two sensors. One fast line.

1

Stereo depth

Use the 25th percentile inside the box, so the wall behind the ball does not win.

2

Lidar at the same bearing

Convert image position to an angle and read the laser range there.

3

Simple sensor fusion

distance = min(stereo_p25, lidar_at_bearing)
One min() operation: fast, deterministic, and easy to debug.
Deep dive · cost mapwhere is it safe?

No floor plan? Draw one live.

Each lidar sweep paints a 120×120 grid: 5 cm cells covering 6×6 m around the robot. 

         ⎧  ∞                    d ≤ 0.18 m
cost(d) = ⎨  1.5·e^(−8·(d−0.18))  0.18 < d < 0.30
         ⎩  0                    d ≥ 0.30 m

Three kinds of cell

  • Blocked — inside the robot radius
  • Expensive — legal, but too close to a wall
  • Free — open floor
The soft-cost band breaks ties: the route with more clearance wins.

Deep dive · motionthe pure-pursuit carrot

Put a virtual carrot on the path. Move it forward.

The “carrot” is a point in software, always 0.5 m ahead on the safe route.

1

A* draws the safe line

The line bends around walls.

2

Place a carrot on it

Pick a point 0.5 m ahead on the route.

3

Chase it

Steer toward it; as the robot moves, it slides forward.

Why not aim at the final goal?

The final goal may be around a corner. The carrot is always on the safe path.

Deep dive · one behaviorstop · look · push

Robot → ball → wall, 40 cm at a time.

The setup

Put the ball between robot and wall. “Away from me” now points at the wall.

The stop–look–push loop

1

Find + center: spin, see the ball, face it squarely.

2

Push 0.40 m: one short shove.

3

Stop + look: find where the ball rolled; aim again.

4

Finish: ball under camera → PUSH_THROUGH; stall → pinned at wall.

Why short segments? Balls drift. Re-measuring lets the next shove correct the last one.
Difficultyproblem → reason → fix

Every hack has a why.

Ignore one noisy alarm

Why: backup_limit false-triggers near the dock.
Fix: ignore it; bump, cliff, and wheel-drop still stop.

Objects become no-go disks

Why: A* may route through an object.
Fix: no-go disks — except for the push target.

Stale sensors restart

Why: docking stops lidar; USB can stall the camera.
Fix: stale timestamps trigger a restart.

Evaluate the deployed .blob

Why: conversion can change model output.
Fix: test the .blob on the VPU.

The router is part of the robot

Why: the bot failed on my home mesh.
Fix: Micro Center → dedicated ASUS router.
