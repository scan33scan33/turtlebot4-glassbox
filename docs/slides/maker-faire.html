Philosophywhy “glassbox”?

Not a black box — a glass one.

You can watch it think. The phone UI shows the live map, the planned path, every detection, the push line, and the skill that’s running.

Black-box robot

  • “Trust the neural net”
  • Fails mysteriously
  • Hard to demo, harder to debug
  • Needs a big GPU / cloud

This robot

  • Vision net only names objects
  • A* + geometry decide motion
  • Every step is drawn on screen
  • Drives are recorded & replayable

ML does one job well (what is that?). Algorithms do the rest (where do I go? how do I push?).

Seethe only neural net in the system

Vision in one sentence.

A neural net is a function trained on millions of photos. You give it pixels; it returns “sports ball, 93% sure, right about here.”

? What it answers

  • What is in the frame? (one of 80 COCO labels)
  • Where in the image? (a bounding box)
  • How sure? (confidence 0–1; we keep ≥ 0.3)
It does NOT decide where to drive.

! Why on the camera?

  • OAK-D has its own VPU (a tiny AI chip)
  • Runs ~6 detections/sec without touching the Pi’s CPU
  • Pi stays free for planning + the web UI
  • Works offline — no cloud, no Wi-Fi needed to see

See · depthhow far is the ball?

Two eyes + a laser = one distance.

1

Stereo depth (the two lenses)

Like your eyes: shift between left & right image → distance. We take the 25th percentile inside the box — so a wall behind the ball doesn’t steal the reading.

2

Lidar at the same bearing

Pixel → angle → look up the laser range in that direction. Lidar is precise on hard edges; stereo is better on soft objects.

3

Fusion rule (one line)

distance = min( stereo_p25 , lidar_at_bearing )

Camera says what. The nearer sensor says where.

Plan · mapwhere is it safe to drive?

No floor plan? Draw one.

Every lidar sweep paints a 120×120 grid (5 cm cells = 6×6 m, robot at the centre). Each cell gets a cost: how bad is it to drive here? 

         ⎧  ∞                     d ≤ 0.18 m   # robot body
cost(d) = ⎨  1.5·e^(−8·(d−0.18))   0.18 < d < 0.30
         ⎩  0                     d ≥ 0.30 m   # free

d = clearance to nearest obstacle (from an OpenCV distance transform). The soft band is a “don’t hug walls” tax — equal-length routes aren’t tied; more clearance wins.

Think of it like a game map

  • Wall / furniture → cost ∞ (impassable)
  • Near a wall → high cost (legal but ugly)
  • Open floor → cost 0 (preferred)

Same idea as grass / forest / water tiles in an RPG — just measured live, many times a second.

build_grid() · ROBOT_R=0.18 · INFLATE_R=0.30
Plan · pathfindingthe algorithm you already know

A* — ~35 lines, on a live map.

If you’ve written pathfinding for a grid game, you’ve written this. f = g + h. We just add the soft cost into g. 

# heap holds (f, g, row, col)
heap = [(h(start), 0, start)]
while heap:
    g, cell = heappop(heap)
    for neighbor, step in MOVES:      # 8-connected, step=1 or √2
        g2 = g + step + cost[neighbor]
        if g2 < best[neighbor]:
            best[neighbor] = g2
            heappush(heap, (g2 + h(neighbor), g2, neighbor))

h = Euclidean distance to goal. Line-of-sight smoothing trims corners afterward — but won’t cut the wall-hug band.

Why it feels smart

  • Replans 3 times a second — a person walking by gets a new route
  • Soft cost in g → paths prefer open space, not wall-skimming
  • Seen objects stamp no-go disks into the grid (except the thing we’re pushing)
  • Same loop routes RPG characters, GPS, warehouse bots

One gotcha we hit

The lidar is mounted +90° from the robot frame. Forget the rotation matrix and the whole map is sideways. The code comment: “without this the whole grid is 90° off reality.”

Skillsa tiny language for tasks

Behaviors are just .toy scripts.

Named skills (SCAN_FOR, PUSH_AWAY, FOLLOW, EXPLORE…) sequenced by a ~300-line interpreter. Readable on a poster. 

# programs/push_ball_to_wall.toy  (simplified)
SET ball = SCAN_FOR("ball", 360)   # spin until you see it
IF ball != NONE THEN
    SET r = PUSH_AWAY(ball.x, ball.y, 0.40)
    IF r == "stalled" THEN
        PRINT "pinned against the wall — done!"
    END
END

Offline-testable with a MockRobot — no hardware needed to check the logic.

Skill primitives

SCAN_FOR FIND PUSH_AWAY PUSH_TO_GOAL PUSH_THROUGH FOLLOW FOLLOW_FAST EXPLORE GOTO

Why a DSL, not a big model?

  • You can read the plan before it runs
  • Fails are specific: stalled / lost / blocked / no-goal
  • Add a behavior = drop a new .toy file
  • No GPU, no API key, no surprise
Talkwords → which .toy file?

“Push the red ball to the wall” → rank.

1 Verbatim trigger

Each program lists trigger phrases. Longest substring win → score 1.0.

"push the ball" ∈ text  →  push_ball_to_wall

Stops a big word-pool from shadowing a short exact trigger.

2 Else: token overlap

Query words Q vs program corpus W (description + triggers):

score = |Q ∩ W| / √(|Q| + 1)

Deliberately dumb and dependency-free. The code marks the seam: “swap in an embedding model here.”

Bonus: colour words filter

“red ball” doesn’t pick a different program — it filters detections by colour after the match.

The mental modelprompt in, script runs

Like Claude Code, not like a VLA.

The same interaction shape as an AI coding agent — you type a prompt and a script runs on the robot. But no neural net chooses or writes the actions.

“push the ball to the wall” → match_program() → push_ball_to_wall.toy → SCAN_FOR · PUSH_AWAY · PUSH_THROUGH

A VLA model (RT-2 · OpenVLA · π0)

  • One big neural net: camera + language in, motor commands out
  • Learned end-to-end from massive robot data
  • Needs a GPU in the loop
  • Powerful — but a black box: you can’t read why it pushed

This robot

  • Your words → a 50-line rule-based matcher picks a hand-written script
  • The script sequences classical skills: YOLO labels, A*, contact geometry
  • Nothing learned end-to-end — the whole loop runs on a Pi
  • Every step readable and unit-testable — that’s the glass box
Same UX as “the model writes a script from your prompt” — with a rule book instead of a model and scripts a human wrote on purpose. A little flexibility traded for something you can fully explain.

Realitythe duct tape that survives a demo

The hacks that make it work.

Depth that ignores the background

p25 of stereo depth in the box — the spatial NN kept reporting the wall behind the ball.

Detections become obstacles

Each seen object stamps a no-go disk into the cost map — except the push target, whose cost is cleared so A* may hit it.

Stalling is the success signal

A push is done when odometry stops moving. The stuck detector doubles as “ball pinned.”

The alarm that’s ignored

Bump / cliff / wheel-drop e-stop instantly. backup_limit cries wolf near the dock, so it’s dropped.

Sensors that heal themselves

Docking stops the lidar motor; USB2 stalls the camera. Stale timestamps trigger auto-restarts.

Eval the deployed artifact

A mis-compiled YOLO head once scored a bogus ~15%. Measure the .blob on the VPU, not just the .pt.

Takeawaysideas you can use tomorrow

What to steal for your own project.

1

Keep ML small and boring

One net, one job (label + box). Let geometry and search do the thinking you can explain on a whiteboard.

2

A* on a cost map is enough

Soft exponential inflation around obstacles → paths that prefer open space. Same code as an RPG pathfinder.

3

A tiny DSL beats a giant prompt

Named skills + a 50-line matcher you can unit-test. Swap in embeddings later if you need to.

4

Show the thinking

Live map, path, detections, skill name. Recording every drive made debugging 10× faster — and makes a great booth demo.

5

Design for the failure mode

Stall-as-success, self-healing sensors, ignored false alarms. Demos die from the boring faults.
